# M8 — Hardening & v1.0: acceptance

The exit gate (MILESTONES §6, M8): budgets met on the i5 · installed on every lab computer by the silent
installer · **a real exam run with ExamMode**, the teacher's notes here · tagged `v1.0.0`.

**Where M8 is.** The teacher asked for a review while hardening (*"review and refactor where it's needed ensure
maintainability, security and scalability"*). That is what is recorded here: §1–§4. **The installers, the release
workflow, updates, the user guide and the classroom trial are not built** (§5). Nothing is tagged.

## 2. What was fixed

**The two that mattered most**

| Finding | What it meant | What was done | Proven by |
|---|---|---|---|
| **The Guard took its orders from whoever said it was ExamMode.** A caller named its own process number, and handed the Guard a list of changes to make — as the system | Any program on a lab computer could write anywhere in the registry or the firewall as the system: its own administrator account, in effect | The Guard finds out who is calling from the connection itself; it is told only what an exam needs, each part checked, and makes the plan itself; its journal folder is closed to other accounts | `tests/windows/guard-channel.test.ts` on Windows Server 2022 and 2025: a program giving ExamMode's own process number *is not heard*; `tests/integration/guard.test.ts`: a caller's own list of changes is refused; `lock.spec.ts` still locks and unlocks |
| **One request could stop the teacher's laptop**, from any computer on the network, with no code: an unreadable address in a WebSocket request, or an upload cut off in the middle of a file | The exam's server gone in the middle of an exam | Neither throws now; nothing a stranger sends reaches an unguarded line; what does go wrong is logged, not shown in a dialog | `tests/integration/hardening.test.ts`, with the same two requests (the reviewer reproduced both crashes first) |

**The teacher's laptop, from the network**

| Finding | What was done |
|---|---|
| Uploads had no limit: one student could fill the disk, and every other student's work would fail | Files per request (500), bytes per file (500 MB) and per request (1 GB), bytes kept per student (2 GB), and 500 MB kept free on the disk; a file too big is said to the teacher, not silently left out |
| The log could be flooded: wrong codes from a computer that was already made to wait; words and lists of any length | Every string and list of the protocol has a size; a waiting computer's wrong codes aren't written down again |
| Any number of connections could be opened and held | 1,000 at most; one that doesn't ask to join within 10 s is closed |
| **One message could put a classmate out of the exam**: a join in their name with their computer's name | Refused while that student's ExamMode is alive (connected, beats coming). *This changes a rule of §2.8 — see §3, row 1* |
| Anyone could report installed apps for 200 made-up computers | 60 computers per address; browsers and remote tools are never offered (M5) |
| Files the laptop couldn't keep (a full disk, a file open in Word) were answered as *invalid*, and the student's ExamMode retried in silence for ever | A 500, an event for the teacher (*this laptop couldn't keep their files*), a line in the log |

**A lab computer**

| Finding | What was done |
|---|---|
| **A student with thousands of files could never back up or hand in** (a Python environment, an unzipped project) | Files go up in parts; the hand-in is the list, and carries only what the laptop doesn't have |
| One failure to make or read the Exam folder was remembered for the whole exam: no hand-in possible | Tried again each time; the hand-in's loop survives whatever is thrown |
| Hand-in retries every 2 s for ever, hashing the folder each time, 40 computers at once | Back off to 30 s, not all at the same moment; a file that didn't change isn't read again; an upload has a time limit |
| The process guard never closed a forbidden program that got a closed one's process number; one that couldn't be closed was never tried again | Numbers that are gone are forgotten; a failed close is tried at the next look; looks that keep failing are told to the teacher |
| A long time with no contact made a record too big to send: the computer could never come back | The record has a size (500 entries, then a count) |
| **A failed unlock was invisible**, and the secret to try again was thrown away first | The Guard keeps the secret and keeps trying; ExamMode says *This computer isn't back to normal yet. Tell your teacher*, writes it down, and tries again |
| The exam a computer remembered (to come back after a sudden stop) was believed as written | The signed announcement is kept with it and checked again |
| A run's id could be anything, and became part of a command line and a folder to delete | A UUID; apps are started as themselves, not through `cmd.exe` |
| Development switches (`EXAMMODE_…`) worked in an installed ExamMode | None do; no menu, no developer tools; windows aren't closed by a key while locked |

**Trust between the two (M7's design, tightened)**

| Finding | What was done |
|---|---|
| A real, signed announcement sent on from another computer was listed with that computer's address | The announcement carries the laptop's own addresses, signed; it counts only from one of them |
| A signed *you're in* made for one student's join could be handed to another | A connection's signatures are for exactly the join they answer |
| The author's key file was locked with a fast key derivation | scrypt (256 MB, about a second a guess) and AES-256-GCM |

**The teacher's laptop with a full lab** (N-03)

| Finding | What was done | Measured |
|---|---|---|
| Every change rebuilt the whole state from the database — every class, exam, event and file — and sent it to the screens | At most four times a second; the classes, exams and lab apps read once; events from where they were; a student's files when some were taken; at most 3,000 events to the screens | `tests/acceptance/load.test.ts`: 100 students, 40 computers' apps, a 20,000-event log, 100 changes every 20 ms — a look takes **2–3 ms**, about 600 KB to the screens |
| Counting the lab's apps was quadratic, on every change | Once per report, only when a report comes | — |
| The announcement had no size limit: a long title in Khmer wouldn't fit in one packet | The title and names have a length; an announcement bigger than a packet isn't sent | the longest possible is under 1,400 bytes (`trust.test.ts`) |
| The live view drew every card four times a second | Only the countdown; a card when what it shows changed | — |
| A hand-in's receipt was given before the files were surely on the disk | Synced first; the database syncs fully on a Mac | — |

**The code itself**

- The layers are enforced: the teacher's side and a lab computer's side don't import each other; only the shell knows Electron; `src/win`, `src/guard`, `src/trust` don't reach into `src/main` (ESLint, with planted bad imports as tests). Two helpers that crossed (`findExe`, `hashFile`) moved.
- One list of the screens' calls, checked against the API and the handlers; one list of event kinds, checked against the feed's words — `ruleChanged`, the most important alarm, had none.
- A log file (`exammode.log`), and nothing that fails is lost in silence: unhandled failures are written down; ExamMode that can't start says so and closes.
- Saving an exam with a file that can't be read no longer leaves an exam behind; the form's buttons can't stick.
- `npm run unlock` exists now (the Guard's `--undo`): the *if something goes wrong* tool the plan promised.
- CI: read-only permissions, a timeout, superseded runs stopped, `npm audit` of what ships (0 found), a trace kept when an e2e test fails, weekly dependency checks. An unused package removed. Stale *M3: not locked yet* comments rewritten.

## 3. Things I decided. Each needs your yes or no

| # | Case | What I made it do | Why |
|---|---|---|---|
| 1 | **A second ExamMode in a student's name, on "the same computer", while theirs is running** | Refused as *name taken*. Before: the first was taken to have stopped, and the student was marked *left — stopped suddenly* | ExamMode runs once on a computer, so a second one with the same computer's name while the first is alive can only be someone else. A real restart has no connection any more, and is treated as before |
| 2 | **The limits** | 500 MB a file, 2 GB a student, 500 MB kept free | A lab exam's work is documents and code; say if a class works with video |
| 3 | **A file too big** | Not sent; a warning line for the teacher; the student isn't stopped | Losing it silently was the alternative |
| 4 | **The screens show the newest 3,000 events** | A longer log is whole in the exported CSV | A day's exam with 40 students has a few hundred |
| 5 | **The Exam folder button on the bar** | Hidden while the computer is locked | It opened Windows' file manager, which the lock stops |
| 6 | **A computer that can't be unlocked** | Says so on the Join screen and keeps trying for 10 minutes | Before, nobody was told |

## 4. Found and not fixed

| Finding | Why it is left | Risk |
|---|---|---|
| **Someone in the middle of the network** (not just re-sending announcements: taking over the wire) can read a student's files and token as they pass, and hand in in their name. Signatures don't hide anything | It needs an encrypted channel keyed to the teacher's licence — a design change, not a patch | Medium. Needs skill and a prepared laptop in the room; the teacher's laptop still holds what it received |
| **The exam code can be found by trying from many addresses** | A limit for everyone would let one computer lock the whole class out. The teacher sees *A wrong code was typed* lines | Low–medium |
| **ExamMode's fuses aren't set** (`ELECTRON_RUN_AS_NODE`, `--inspect`) | They are set when the app is packaged: with the installer (§5) | High until then — but there is no installed ExamMode until then either |
| Desk writes (saving an exam or a class) share the classroom's open transaction | Needs the store to own the queue; no failure seen | Low: a failed turn in the classroom could take a just-saved exam with it |
| Finding out who made a new program blocks the look at the processes for 1–3 s on a slow computer | Once per new program; needs the lookup moved to the background | Low: a second forbidden app opened in that moment is closed a little later (N-02's 1 s is at risk there) |
| Closing a program that is slow to die holds ExamMode's main process up to 3 s | Needs an asynchronous wait | Low |
| **Locking isn't fast enough to be sure of N-10 (3 s) on the i5**: about 50 small programs are started one after another (1.8–2.2 s on GitHub's computers) | Needs a lab computer to measure before changing the Guard's order of work | Medium: the budget may be missed on the slowest computer |
| At time up, a whole lab's hand-ins are checked (SHA-256) and moved one after another on the laptop's one thread, with no limit on how many at once | 30 simulated students hand in within 0.6 s; needs the measurements of a real lab before it is worth changing | Low at 40 students; to be measured at 100 with big files |
| A look at the processes takes a little longer than it has to (a list is rebuilt for each process); the screen after the exam draws every file of every student | Small | Low |
| The class list isn't signed (M7) | As decided there | Low |
| A PowerShell quoting hole in the publisher lookup (curly quotes in a folder's name) | Runs as the same user: nothing is crossed | Low |
| Type-aware lint rules (`no-floating-promises`) aren't on; `runStudent` is one long function | A larger change than its worth this week | — |
